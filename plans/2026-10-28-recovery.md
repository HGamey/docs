## 目标

以下摘自用户 2026-10-28 的任务书。

**核心场景：**

1. 在网页上下指令，例如「优化 xxx 游戏的超分方向」，新建一个任务。
2. 由 agent 自动接取，或由人指派。
3. 能看到每台手机的占用情况和当前在做什么。
4. 能看到任务的探索过程、agent 的留言和讨论、当前结果，以及过程中的图像和图表。
5. 人可以在任务里给指导，agent 采纳或回复。
6. 最后交付一个别人拿到就能直接用的成果单元（自训练模型或配置参数）和一份报告。

**最让用户失去掌控的地方：**

- 网页、后端、CLI 互相冲突、彼此不一致。
- 外部 agent 对人不可见。
- agent 的入口不清楚：每轮该做什么，应当由 CLI 告诉它，而不是让它读源码。

**约束：**

- agent 在平台外部，不在平台内运行。
- 要有权限隔离：没完成规定的事，就不能更新任务进度。
- 人和 agent 是异步的：某个方向在等人时，agent 不停下，继续其他方向。

**验收分三层：**

- 工程层：CI 四个套件通过。
- 流程层：人和 agent 在生产节点上只用网页和 CLI，就能走通核心场景。
- 领域层：交付的成果真的达成游戏目标。

## 关键流程与状态归属

| 概念 | 落在哪里 |
|---|---|
| 任务 | research 对象（`harness-ops/node/node_research.py`，SQLite，带版本号的条件写入）。`owner` 是已注册的 agent。 |
| 留言 | note 对象，带 `reply_to` 和 `decision`（adopt、defer、reject）。 |
| 交付 | research 的 `deliverable`：总结、产物、适用范围。 |
| agent 身份 | 每个 agent 有自己的 token（`pf-node agents token`），写入都记在它名下。每轮入口是 `pf-node checkin`（`agent_duties.py`），列出欠的事和每轮做法。 |
| 执行 | job（持久队列），用 `--research` 关联到任务。研究只指定一台手机时，写任务默认只占那台；否则用 `--resource device:<串号>`，都没有就是全局。任务结束自动释放预留，进程状态确认不了的由管理员一步重置。 |
| 设备锁 | phonefarm 的锁存储。mbp1 自 20:05 起是 layout 2，每台登记过的手机有自己的 lane；全农场的 devlock 是全局域，持有时挡住所有 lane。 |
| 实验代码 | HGamey/experiments，用 `--experiment <提交>` 运行。数据随任务产物留在节点，报告写进 docs。 |
| 网页 | 首页显示手机占用、进行中的任务、Agent；研究页显示负责人、交付、运行、留言。 |

## 已定决策（2026-10-28）

**产品与开发：**

- 任务用 research 承载。
- 信任 agent，防的是 agent 遗忘职责，不是攻击。
- 直接推 main。
- 前端功能优先，不写解释性文案，样式以后另行重做。
