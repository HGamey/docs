## 目标

以下摘自用户 2026-10-28 的任务书。

**核心场景：**

1. 在网页上下指令，例如「优化 xxx 游戏的超分方向」，新建一个任务。
2. 由 agent 自动接取，或由人指派。
3. 能看到每台手机的占用情况和当前在做什么。
4. 能看到任务的探索过程、agent 的留言和讨论、当前结果，以及过程中的图像和图表。
5. 人可以在任务里给指导，agent 采纳或回复。
6. 最后交付一个别人拿到就能直接用的成果单元（自训练模型或配置参数）和一份报告。

**最让用户失去掌控的地方：**

- 网页、后端、CLI 互相冲突、彼此不一致。
- 外部 agent 对人不可见。
- agent 的入口不清楚：每轮该做什么，应当由 CLI 告诉它，而不是让它读源码。

**约束：**

- agent 在平台外部，不在平台内运行。
- 要有权限隔离：没完成规定的事，就不能更新任务进度。
- 人和 agent 是异步的：某个方向在等人时，agent 不停下，继续其他方向。

**验收分三层：**

- 工程层：CI 四个套件通过。
- 流程层：人和 agent 在生产节点上只用网页和 CLI，就能走通核心场景。
- 领域层：交付的成果真的达成游戏目标。

## 关键流程与状态归属

| 概念 | 落在哪里 |
|---|---|
| 任务 | research 对象（`harness-ops/node/node_research.py`，SQLite，带版本号的条件写入）。`owner` 是已注册的 agent。 |
| 留言 | note 对象，带 `reply_to` 和 `decision`（adopt、defer、reject）。 |
| 交付 | research 的 `deliverable`：总结、产物、适用范围。 |
| agent 身份 | 每个 agent 有自己的 token（`pf-node agents token`），写入都记在它名下。每轮入口是 `pf-node checkin`（`agent_duties.py`），列出欠的事和每轮做法。 |
| 执行 | job（持久队列），用 `--research` 关联到任务。会改设备状态的任务结束后停在 blocked，核查后 release。 |
| 实验代码 | HGamey/experiments，用 `--experiment <提交>` 运行。数据随任务产物留在节点，报告写进 docs。 |
| 网页 | 首页显示手机占用、进行中的任务、Agent；研究页显示负责人、交付、运行、留言。 |

## 已定决策（2026-10-28）

**产品与开发：**

- 任务用 research 承载。
- 信任 agent，防的是 agent 遗忘职责，不是攻击。
- 直接推 main。
- 前端功能优先，不写解释性文案，样式以后另行重做。
- **功能先做完，前端再按功能改；不等用户验收**（11:10）。用户原话：「先把功能做完，然后前端改得配合功能，不用等我验收，继续向前，我有空就会自己验收的」。
- **给用户的留言和待办发到 kamico.closure.moe**。那是本机的 meiso-board，身份 `HGamey-lead`，由首席一人发。
  - 待办用「过目」「动手」卡；用户点了，看板会叫醒首席的 HAPI 会话。
  - 每天最多 5 条留言，同时最多 3 张卡。
- 实验代码不进 main，放 experiments 仓库；运行数据迁到 docs。
- token 暂不轮换。
- 首页的新建按钮改为新建任务，GOL 目标降为可选方法。
- **能恢复，就不设防**（10:52）。用户原话：「生产手机队列卡死了可以重置。不用等什么手机都释放再部署（之前的部署规则，过于严格了，我怀疑之前也有大量的无效测试+防御代码在项目中，都可以移出），我手机都有adb了。没有那么脆弱。我们只要有恢复流程不就可以了吗？」落实为四件事：
  - 部署不等手机空闲；
  - 队列卡死由 glm-ops 直接重置；
  - 去掉「任务结束后停在 blocked、等人放行」这道闸；
  - 清点全仓的防御代码和无效测试，按清单分批移出。「移出」就是直接从 main 删，git 历史里留着，不另建归档仓库（用户 11:05 确认）。
  
  研究层的权限隔离（交付闸门、各自的 token、负责人不被抢、交付带产物）不在此列，保留。
- 任务页显示图表，做法是引用任务产物中的文件；以实际使用后的验收为准。
- `skills/hgamey-research/SKILL.md` 可以更新。

**节奏：**

- **team-loop**：本机 cron 每 5 分钟检查一次，脚本在 `/HGamey-dev/HGamey/team-loop/`。
  - agent 的会话空闲、并且距上次唤醒已满 30 分钟，就叫醒它做下一轮。
  - 开发 agent 在自己的笔记目录写 `loop.json`：
    - `working`：继续叫醒；
    - `waiting`：不再叫醒；
    - `done`：不再叫醒，并通知首席。
  - 在该目录下建 `STOP` 文件，所有唤醒都暂停。
- **首席每 4 小时回顾一次**：对照本文检查差距、两个 agent 改同一处、卡住没人管的事、宣称完成的证据，然后调整分工并更新本文。

## 阻塞与下一步

**阻塞：**

- 红魔的厂商刷新率控制器会在测量窗口里把屏幕压到 60 Hz。正式 A/B 中超分加插帧臂 6/6 作废，0 个有效对。这是研究侧的问题。
- 只有 mbp1 有手机，真机相关的验收只能在生产节点上做。
- GOL 密钥需要用户重新填写。GOL 是可选方法，不阻塞核心场景。

**下一个宏观验收点：** 功能都上了 mbp1 以后，做一次端到端验收，不等用户：

1. 由 agent 在网页上扮演人，建一个小任务；
2. glm-researcher 接取，跑任务，并发带图的留言；
3. 扮演人的 agent 在任务里给指导；
4. glm-researcher 回应；
5. glm-researcher 交付报告。

全过程只用网页和 CLI。用户有空时在看板上收到「过目」卡，自己再验一次。

**之后：** 前端统一改一轮，让页面配合功能。
