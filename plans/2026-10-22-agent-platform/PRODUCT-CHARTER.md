# 产品准则与验收标准

2026-10-22。来源：项目负责人与开发 Agent 的两轮目的讨论、使用经历及维护者手册审计。本文记录产品决定，不替代逐项实现与测试证据。修改决定时保留旧值、原因和日期，不能用新口径覆盖旧实验。

## 我们共同建设什么

让外部 Agent 使用远程真机，系统性优化指定游戏或系统，探索多种方向，完成可复现实验并留下可审核结果。平台提供稳定的设备、资源、任务、研究状态、证据与协作能力。Agent 的选择与推理可以发生在任意工具里；prompt 加平台功能即可形成 harness。

人异步给技术指导、提供数据或现场协助、评价图片和视频。需要人的方向可以阻断；有其他可行方向时，Agent 应继续排序、实验和验证。平台负责保存依赖和反馈，外部 Agent 决定研究优先级。如果所有方向都受阻或预算用完，应记录原因并可恢复地空闲，不能靠无意义轮询或虚构工作维持忙碌。

## 已确认且不能在实现中悄悄改变的决定

| 决定 | 实现与验收要求 |
|---|---|
| 外部 Agent 是主要使用者 | 不使用 GOL、不调用平台内置模型，也能完成完整流程；GOL 是可选方法客户端 |
| 网页与 CLI/API 同等优先 | 同一对象、状态与操作使用同一合同；每批同时验证两种入口 |
| 首批主线是多机、分发、排队、结果 | 优先完成可走通的使用路径，避免把增加命令数量当完成目标 |
| 人与 Agent 异步协作 | 请求持久化、标明依赖；一条路线等人不阻塞其他路线；沉默不算批准或评价 |
| 共享研究状态独立于聊天工具 | 目标、方向、实验、证据和反馈可接续；不要求上传私有聊天历史 |
| 人可看屏和接管 | 观察、操作与测量有明确 ownership 和干扰约束；另一设备不被无关接管阻断 |
| 支持性能与画质权衡 | 用户可事先选择预算和判据；原游戏路径是主基线，模块 ms 也是合法目标；不强制打败双线性 |
| 实验判据先于候选结果冻结 | 可探索新目标，但新目标产生新实验版本；不后改旧结果的及格线 |
| 能力按实例验证 | 隐藏 adb/hdc 等传输差异，显式暴露权限、能力、测量来源、条件和未知；Android 能力不外推到 Harmony |
| 证据包括失败与未知 | 原件、派生统计、结论分开；缺失不填零；进程结束不等于恢复完成 |
| 原始数据留在明确位置 | 入口域名、执行宿主、数据位置分开；索引可共享，原件迁移须显式执行 |
| 直接 commit/push | 小批验证后提交，不新开 PR、不 force push、不夹带他人修改或凭据 |

## “可用”必须说清适用范围

以下是不同层次的证据，不能互相代替：代码存在 → 构建/单测通过 → 模拟协议或故障场景通过 → 指定设备/版本实测通过 → 指定使用流程端到端通过。代码支持、该设备当前可用、该场景已经验证也必须分开。

第一批端到端验收：外部 Agent 与网页看到两节点设备和任务；分发已有游戏清单；提交多条工作；一个方向等人或设备离线时另一个继续；客户端断开或服务重启后找回同一任务；人能看屏、接管和归还；任务结束后能看到恢复状态；只读访问者能发现并下载一般任务的结果和失败证据。核心流程不以 GOL 目录或特定命令名为准入条件。

只有本地设备枚举、若干 probe、单元测试通过时，应写“这些基础检查通过”，不能缩写成整个平台“已可用”。有已知限制不一定是 bug，但只要阻断上述必需路径，就仍是交付缺口。

## 如何判断思想是否对齐

评价架构决定与可观察行为，不从遗漏的章节推断个人动机。愿意用上述目标和验收共同工作，即可在实现上分批改进。若坚持必须由内置 Agent 控制一切、人工等待必须停全局、只支持特定优化格式才能发现结果、或以单测代替端到端验收，就与已确认产品方向冲突，应明确记录并讨论。

维护者手册对照见 [MAINTAINER-REVIEW.md](MAINTAINER-REVIEW.md)。当前证据没有证明作者持有这些冲突立场。

## 持续记录约定

- 每次用户消息记录原意、原文或明确标注的摘要，以及导致的决定/修正；敏感凭据脱敏。
- 共享仓库只保存产品决定、理由、变更与验证；本机任务目录保存可获得的对话摘录和原文件来源清单。
- Agent 的总结、用户的原话、附件作者的报告、源码推断、独立实测分别标明。
- 对话存档的覆盖范围必须写清，不能把当前可见上下文的回顾称作完整历史导出。
- 后续开发持续更新 [todo.md](todo.md) 和批次验证记录；新 Agent 先读本准则及讨论记录。
