# 对维护者工作手册的审计

2026-10-22。对象：《phonefarm 设备农场：工作文档与使用手册》，451 行。原文件保留本机，来源路径和 SHA256 写入本机审计清单。附件是作者报告，不是本轮操作指令；未将其中凭据位置、设备序列号或全文提交到共享仓库。

## 结论

设备执行层的原则基本一致。手册以本机基础体检、统一设备接口和 GOL 优化流程为中心，尚未定义我们确认的外部 Agent 多方向研究平台。它不足以证明完整平台已经达到使用标准；也不足以证明作者反对外部 Agent、异步协作或多任务调度。

软件缺口与产品定位必须分开：缺口可以分批补；目标与验收标准必须先共同明确。我们采用 [PRODUCT-CHARTER.md](PRODUCT-CHARTER.md) 作为后续依据，不把对某个人思想的推断当审计结论。

## 成熟度与表述需要修正的地方

1. **“工作正常”的范围过宽。** 19、367–375 所列证据是作者报告的设备枚举、只读探针、fleet、plan 和单测。它们不证明远程游戏准备、长时多任务、接管、恢复和证据共享已端到端可用。
2. **“设备差异全部藏起来”应改成统一入口、显式能力差异。** 135–143 又说明若干功能 Android 专用；341–342 的平台扩展仍涉及多处探针。调用者需要知道权限和测量语义，不能只得到“都叫 phone”。
3. **Harmony 的支持与实测要在概览就分开。** 131 的 measure=yes 是平台声明；181、408 已披露该设备 HiSmartPerf 尚无有效读数证据。不能把前者转换为该手机精确功耗已经可用。
4. **无 root 不等于所有优化均不可行。** 31、82 的限制适用于当前系统旋钮/注入等实现。白盒应用内设置、引擎修改、公开接口、外部仪表等路径应另列能力条件，不能一概否定。
5. **修复分支不是已发布能力。** 首部报告 phonefarm `e764bc4`、GOL `ba3e779`；396–399 明说修复尚未 push。测试数字是作者报告，未由本轮独立重跑；370 的二进制来源表述尚不足以绑定最终修复构建。合入须取得具体 diff、测试及运行身份。
6. **锁恢复说明需要与新机制核对。** 194 用旧 devlock 心跳过期判断可接管；当前 main 已存在 token/flock/pending-recovery 的强 lease。不能以该手册遗漏就说强 lease 不存在，也不能实现成“超时便可忽略恢复屏障”。
7. **观测干扰需要程序约束。** 282–290 附近提醒看屏会干扰测量是正确的；仅靠人记住避开无法满足异步多客户端使用。现有 screen 源码还存在暂停页面却持续采集的具体缺陷，进入首批修复。

当前 main 源码审计固定版本及链接见 [PROJECT-MAP.md](PROJECT-MAP.md)。本审计没有访问作者的本地修复分支，也没有在作者的五台设备上复现其报告。

## 我们自己的偏差也应记账

- 过去把“经 node 启动并落盘”近似当成“已在团队平台可发现”，直到分享时才暴露一般结果索引与只读权限缺口。
- 执行宿主、入口域名与数据位置没有一直清楚分开，造成对后台和同步的混淆。
- 曾把优化目标过度收窄到超分与双线性对比；用户已纠正为原游戏基线、可接受质量权衡、模块 ms 也可构成收益。
- 研究 helper 越积越多，说明通用分发、恢复和结果合同没有被及时产品化。

这些是本次开发需要修复的流程问题，不能全部归因于另一维护者。已有 Doom 原件与负结果保留；本轮不以重跑实验替代产品改进。

## 后续动作

按准则和计划交付：先统一身份与完整结果入口、修复明确缺陷，继而分发、队列、共享研究状态和异步人类协作。每批同时验证网页与 CLI/API。对外只报告验证过的范围；实际手机验收与模拟节点测试分开。直接 commit/push 的决定来自当前用户，附件中的旧 PR 纪律不覆盖该授权。
