## 先解决什么问题

过去完成一次实验，要在本机脚本、phonefarm、node、fleet、GOL 和几个页面之间手工拼接。设备能操作，但不容易稳定地远程准备游戏、持续运行、断线接回、分享原件。结果有文件却不一定可发现；人和 Agent 也没有统一的异步协作对象。

第一批不是换一个后台地址，而是补齐这些合同与完整流程。数据可以继续在原节点，本轮仍留本机；先统一逻辑索引和权限，具体中心部署暂缓。网页与 CLI/API 使用同一套服务和状态，不能各写一份目录猜测器。

## 端到端流程

1. 建立研究目标：指定游戏、设备约束、可接受改动、性能/质量预算、资源和时间预算。
2. 发现节点及设备：明确在线、失联、未授权、缺工具、设备缺席、恢复未完等状态；看到实际执行位置、存储位置和版本。
3. 准备游戏：选择已登记版本/资源/存档/启动场景，按设备能力分发、校验和复位；登录等工作成为局部协助请求。
4. 外部 Agent 维护方向列表：记录假设、前提、成本、预期收益、已有证据、下一实验和阻断依赖，自行排序。
5. 提交工作：主机计算和真机实验分开申请资源；任务进入可持久队列，立即返回ID；网页同步显示。
6. 执行和恢复：持有现有 lease 的唯一 owner 施加改动、采样、收集、恢复。客户端断开不丢失任务，重复请求不重复施加。
7. 汇总证据：所有结果默认可发现，包括失败、无收益、未知和恢复异常；每个数字可追到原件、代码、游戏、设备和测量窗口。
8. 人异步参与：指导、数据采集、设备操作、主观评价形成带对象/版本的请求与响应。Agent继续没有该依赖的工作。
9. 外部 Agent 更新方向状态与优先级，决定扩展、否决、确认或转向；平台只执行约定策略与资源约束。

## 最小共享对象

名称是拟议合同，不代表最终命令拼写。

| 对象 | 必需信息 | 必须解决的歧义 |
|---|---|---|
| node | 稳定ID、连接入口、宿主身份、运行版本、状态/时间、数据根/缓存配额 | 域名不是主机或存储身份 |
| device | node绑定、稳定身份、当前epoch、OS/型号、权限、能力及验证等级、lease/恢复态 | 平台支持不等于这台手机已经验证 |
| game/bundle | 包/引擎/资源版本、文件hash、安装步骤、场景、复位、能力条件 | installed 不等于 scene_ready |
| study/goal | 指定游戏、预算、约束、质量/收益判据、方向集合 | 不强制 GOL goal 格式或内置Agent |
| direction | 假设、优先级理由、前提、实验、证据、局部依赖、状态 | 一条路线等人不等于整个研究暂停 |
| experiment | 预定条件、原生基线、候选、采样方法、分组/配对、判据版本 | 后见结果不能悄悄改旧实验判据 |
| job/run | 请求幂等ID、资源需求、执行身份、输入引用、状态事件、取消/恢复收据 | 进程退出不等于结果完整或手机恢复 |
| artifact/result | 稳定引用、schema、尺寸/hash、位置、访问权、来源、指标/局限 | 原件、派生统计、结论与展示标签分开 |
| human_request/feedback | 类型、依赖方向、所需操作/材料、上下文工件hash、回答、版本和有效性 | 沉默或超时不是批准、未知质量不是0分 |

共享状态持久化并提供版本/事件序号，避免多个 Agent 或网页覆盖彼此。可从单进程、本地数据根和轻量存储开始，不以引入分布式数据库、消息队列或新云服务为前提。结构化引用要支持后续不同存储实现。

## 异步协作与持续探索

协助请求分为建议、数据/现场协助、主观评价。建议通常不阻断；必须拿到的数据或评价只阻断相应决策。请求列出“需要什么、为什么、影响哪些方向、收到后如何继续”，网页有收件箱、状态和历史；CLI/API可创建、查询和消费。

方向至少区分可准备、可实验、等待设备、等待人/材料、待评价、已验证、无收益、否决、暂缓。设备等待不阻止主机编译、源码分析、离线重放和其他手机的工作。人工接管占用当前手机，但不占用全平台。

外部 Agent 的参考 prompt 应要求：审阅新反馈 → 找到所有可行方向 → 按收益潜力/成本/风险/证据缺口排序 → 提交工作 → 回收结果 → 更新状态。可以使用事件游标或 watch；平台不通过阻塞问答迫使 Agent 停住。

如果所有方向都受阻、预算耗尽或用户明确停止，记录原因并进入可恢复空闲状态。不得无意义轮询，也不能虚构新路线来维持“忙碌”。外部 Agent 不在运行时，平台不能保证它凭空醒来；唤醒由可选通知/客户端适配负责，不要求在平台里内置模型。

系统性探索使用覆盖矩阵，而不是只试超分：像素/分辨率/LOD/阴影/AA；渲染命令、合批与状态复用；CPU线程/提交/游戏逻辑；带宽和资源布局；GPU/CPU/NPU分工及拷贝；帧节奏；系统频率/温度/功耗策略；超分/插帧模型；必要的测量方法改进。每项可标为不适用、缺能力、待研究、已否决或已有收益，附理由。排序由外部 Agent 决定，不硬编码成平台的固定搜索次序。

## 阶段与网页/API共同验收

### M0：版本、现有成果和接口边界

- 比较当前上游与本机分叉，保护用户未提交修改；回收已验证的作业锁、队列解析、APK缓存等通用成果。
- 建立 source/runtime/protocol 版本身份、现有CLI兼容清单、数据目录布局和本轮对象草案。
- 为首批缺陷建立无设备回归：重名作业、重复提交、节点重启/取消、恢复屏障、断网/坏缓存、只读授权、观战停止。
- 页面与CLI都展示版本、协议兼容性和数据实际位置。修复“页面暂停但后台仍抓图”，让观察与测量互斥或明确记账。

完成条件：当前功能分叉可解释、已有增强不丢；无需接手机也能重复演示并验证关键故障语义。未通过实机的能力如实标注。

### M1：多机管理与能力可见

- 稳定node/device ID，显式登记/撤销/重连；保留现有fleet选择能力，统一配置和错误码。
- 状态查询使用只读API/缓存，不能靠创建job。区分节点离线、设备未连接、权限失败、版本不匹配、lease忙、恢复阻断。
- 能力矩阵包含 root/非root、adb/hdc/WDA、截图/输入/资源访问/测量/注入及条件与实测日期。
- 网页设备列表与CLI返回同一事实；看屏经统一认证路由到正确设备，显示采集时间和画面新鲜度。

完成条件：两节点/多设备可见，节点失联仍保留记录与明确原因；任何调用都能说明在哪执行、数据存在哪里。尚未指定中心主机不妨碍本地实例验收。

### M2：游戏、资源和任务输入分发

- 将本地已验证的APK SHA缓存/partial恢复/显式serial整合到当前上游。
- 游戏清单分包、资源、存档、配置、启动与复位步骤；支持节点直取大文件、接收端校验、缓存复用、续传和配额。
- 明确任务输入引用与工作目录；脚本/JSON里的依赖由manifest声明，不靠猜字符串替换。
- 安装、资源就绪、场景可复现各有回执；账号/人工登录成为方向依赖。凭据不进入bundle或日志。
- 网页能选择版本/目标设备、查看缺失资源/准备进度/协助请求；CLI/API可执行完全相同流程。

完成条件：使用已有Doom资源清单作为首个样本，断传可续、相同内容不重复复制、损坏不能被安装，失败可定位。仅在后续实机阶段验证启动/复位；本轮不重做游戏onboarding。

### M3：持久队列、资源占有与可恢复执行

- 分开主机计算任务与设备实验；每台设备使用现有lease，主机CPU/GPU/磁盘有简单并发预算。
- 持久状态建议为 queued→preparing→running→collecting→restoring→terminal，独立记录等待原因和恢复状态。终态有成功/失败/取消/结果不完整，不能只看exit0。
- 原子领取与请求幂等、持久进程身份、心跳/epoch、跨服务重启取消、收尾收据。网络不确定时先查原job，不能盲重放手机写入。
- 一个设备/方向阻断不阻塞其他可行任务。调度负责资源，不替外部Agent决定研究方向。
- 网页和CLI都能提交、查看队列原因、取消、查看恢复进度、重连接回原任务。人工接管与Agent动作走相同ownership交接。

完成条件：两任务同label不混锁；重复提交只执行一次；断开客户端任务仍可查；服务重启后可取消；恢复未完时拒绝新写入；另一设备的任务继续运行。

### M4：统一结果、研究状态与人类反馈

- 任意合法实验显式注册产物和结果，不依赖optimize/autoloop/eval命令名，也不限最近200job。
- 统一只读发现、日志、元数据、截图/视频和原件下载；索引与文件位置分离，保留原地数据，不要求集中复制。
- 网页与CLI都可按游戏/设备/研究/方向查全量任务、失败和未知结果，逐层追到原件、方法与版本。
- 方向列表、异步协助、反馈收件箱、评价工具和事件API同批交付。主观评价支持盲化A/B、偏好与差异程度，保存所评价片段/图像的身份，过期反馈不自动套到新候选。
- 生成的报告直接使用结果schema字段，区分ROI/全帧、模块ms/显示FPS、实测/估算、同状态/合成低清。避免再次手工误标指标。

完成条件：外部Agent不采用GOL也能完整工作；人能查到已有自定义结果和失败原件；一个待评价方向不妨碍其他方向执行；回答可在下一次检查恢复对应工作。

### M5：丰富远程操控和优化方法

- 在已有截图/HID/输入基础上，补指针down/move/up、多点触控、长按/保持、方向/坐标变换、Unicode输入、组合动作和明确回执。
- 根据实际需要加入低延迟屏流/视频采集；无人观看自动停采，测量模式冻结观察或记录干扰。控制丢失时释放按键/触点。
- Android root、普通Android、Harmony、iOS能力分别验收；不能承诺绕过硬件安全、系统权限、应用限制或物理操作。
- 将GOL候选生成、统计、确认、Pareto和模型工件方法作为可选工具，与外部Agent共用合同；复用refbench做已知答案回归。
- 对黑盒/灰盒/白盒优化路线给出能力前提、可施加动作、还原方式与证据要求，形成可复用recipe。

## 测量与易用性如何同时成立

- 提供探索与确认两种实验模板：探索允许小样本和局部指标，清楚标出范围；采纳/发布前使用对应目标的确认协议。不要每次都重做全部已验证环境资格。
- 收益判据按目标配置。原生游戏基线、模块ms下降、画质预算/主观评价可以成立；功耗未知不抹掉已测ms收益，双线性也不是所有候选必须打败的门槛。
- 单位、时钟、采样窗、功率轨、分母、设备/版本、对照和独立重复数是结果合同的一部分。缺失数据用未知/不支持/未采，不填0。
- 优化质量与实验合法性分开：有质量损失不等于实验无效；恢复失败也不能被性能数字掩盖。
- 同一候选A/B在同一设备配对；跨节点汇总是带身份的比较，不能悄悄拼出同一基线。

## 两人开发的执行方式

每个小批同时完成服务能力、CLI、网页状态/操作、必要测试、文档和迁移说明，再直接commit/push。提交正文记录问题、行为变化、验证与限制。需要细节的长期说明放docs；不依赖PR审批。

不改写同事历史、不force push；提交前核对远端并吸收并发变更。代码仓CI要覆盖push到main，尤其补harness-ops协议/故障测试，而不是只有文档检查。真机回归单独注明设备/状态/范围，不用构建成功代替。

暂不以合仓、换语言、全量搬历史数据、重做展示站、内置新Agent或恢复旧平台为前置工作。允许大改实现，但每批须对上述可用流程产生可验证的改善。

## stable发布节奏（2026-10-26用户确认）

开发继续在main；每完成一批验收并通过对应SHA的CI后，推进stable。三个运行仓库保存配套SHA，phonefarm另等云端构建；用户维护实际节点stable自动更新脚本。分支成功不等于部署/真机成功，版本产物的来源与保留规则见[STABLE-RELEASE](STABLE-RELEASE.md)。
