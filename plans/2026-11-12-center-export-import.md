# 中心数据按任务导出 / 导入（2026-11-12，用户要求）

**用途**：迁移中心节点。在原中心的网页上按任务选择要导出的数据，打包成一个 zip；在新中心上用命令行把 zip 加进本地数据。

11-11 把中心从 macmini-3 迁到蓝区 ThinkCentre 时，是整目录 rsync 过去的，出了两类问题：

- 登记结果、盲评素材和游戏资源里记的文件身份（inode、ctime）全部失效，要手工校验后重新绑定。
- 没法只迁一部分数据。

这个功能要把这两件事都解决。

## 切分单位

一个**任务**（研究对象 `kind=research`）的数据包括：

| 数据 | 归属方式 |
|---|---|
| 研究库里 `research_id` 等于该任务的全部对象：任务本身、备注、方向、盲评请求、盲评回答 | 每个对象都带 research_id；要带上完整的 revisions、events 和相关 operations，不能只带最新版 |
| 方向之间的 dependencies | 属于该任务的方向 |
| 作业目录 `_jobs/<作业>/`，包括 meta、日志和 out | 作业 meta 里的 `research_id` |
| 登记结果（`_results` 里的行） | 结果的 `research_id` |
| 研究附件 `_research/attachments/<id>` | 被该任务的 revisions 或结果引用的附件 |

**一个任务的这些子数据必须全选或全不选**（用户的要求）。界面上只能勾选任务，服务端也要校验，不接受半个任务。

**没挂任务的数据**：1078 个作业里只有 260 个带 research_id，另外 818 个以及没挂任务的结果和附件，合成一个特殊分组"未归属任务的数据"，可以像任务一样整体勾选。不这样做，全量迁移会漏数据。

**接续任务**：仍然各算一个任务，可以单独勾选。界面上按任务链分组显示，提供"整条链"一键勾选。只导入子任务、没导入父任务时允许导入，导入报告里列出悬空的引用。

**不在这次范围**：游戏资源缓存（可以重新准备）、节点目录、agent 账号和 token、设备登记、掌舵和查看密码、平台配置。这些不属于"任务数据"，迁移时另外处理。导出清单里要写明"不包含这些"。

## zip 格式

- 用 zip64，服务端流式生成，不能整包放进内存。全量大约 50 GB。
- 根目录放 `manifest.json`，内容包括：
  - `schema: hgamey/center-export@1`
  - 来源中心的 node_id、主机名、导出时间、平台版本
  - 每个任务：ID、标题、对象数、作业、结果、附件
  - 每个文件：zip 内路径、大小、sha256
- 研究库的行按表导出成 JSON Lines，要求原样，导入时能逐行写回。
- 作业在从节点上跑、原件还没收回中心的：导出前先收回来。收不回的（比如从节点离线）在 manifest 里逐个标"未带原件"，界面上也要提示，不能悄悄缺。

## 导出界面

- 位置建议放在「更多」→「数据导出」。需要掌舵权限，因为导出的是全部数据。
- 任务列表要有：
  - 筛选：状态、负责人、时间、标题搜索
  - 每个任务的作业数和估算大小
  - 任务链分组
  - "未归属任务的数据"分组
- 勾选后，在服务端生成导出文件，显示进度，完成后给出下载链接。下载要支持 Range，大文件可以断点续传。
- 生成的导出文件放在中心的导出缓存里，有保留期限，界面上能删除。

## 导入命令行

在目标中心本机运行，例如：

```
python3 harness-ops/node/center_import.py <zip> --data-root <中心的 phonefarm 目录>
```

命令名由实现者定，写进 harness-ops 的文档。规则：

- **默认只做检查并打印计划**：要导入哪些任务、作业、结果、附件，哪些已存在，哪些冲突，哪些引用会悬空。加 `--apply` 才真正写入。
- **先校验后写入**：写入前先校验 zip 里每个文件的 sha256，有任何一个不对就整体拒绝。
- **要么全部成功，要么不改动**：失败时目标中心的数据保持原样。
- **幂等**：同 ID、同内容的跳过，所以同一个 zip 导两次结果一样。同 ID、不同内容算冲突，整体中止并列出冲突。
- **重新绑定文件身份**：导入后，登记结果的源文件按导入后的文件重新记录身份，前提是 sha256 和 manifest 一致。这正是 11-11 迁移踩的坑，导入后结果原件和盲评图片必须能直接打开。
- **服务可以停**：可以要求先停中心服务。脚本检测到服务在跑就拒绝，并提示怎么停、怎么重启。如果能安全地在线导入更好，由实现者判断。

## 实现中定下的细节（11-12，Claude-Sub 提问，lead 定）

1. **自增序号要重排。** revisions.sequence、events.sequence 和结果表的 sequence 是整个库的自增位置，导入时接着目标库的最大值往后排，并保持原来的先后顺序。其余列原样写回，`at` 等时间保留原值。判断"同 ID 同内容"时不比较这几列。
   - 后果：导入的事件会出现在目标中心事件流的末尾。往空中心导入没有影响；往在用的中心部分导入时，订阅事件的 agent 会把它们当新事件看到。
   - 对策：导入报告和命令行帮助里写明这一点，建议往在用的中心导入前先暂停 agent。
2. **从节点作业要带上 job_targets 的那一行。** 导出时还没结束的作业，照样导出当时的目录，在 manifest 里标"未结束"，导入后显示为丢失。
   - 导出界面在勾选时要提前提示：哪些任务带着未结束的作业。这样可以先等它们结束再导出。
3. **只支持离线导入。** 检测到本机正在运行指向目标数据根的中心服务，就拒绝导入，并提示怎么停、怎么启。
   - 检测要同时认两种启动方式：执行节点用 `--data-dir`；生产中心用 `--phonefarm <目录>`，数据根就是这个目录本身（见蓝区中心的 run_center.sh）。路径要先解析符号链接再比较。
   - 写入时先放进暂存区，再备份三个库（研究库、结果库、job_targets），失败就整体还原。
4. **只重新绑定导出时核实过的源。** 导出时，当前身份戳或已登记的 sha256 对得上的结果源，记为"已核实"。导入时只重新绑定这些，并且绑定前要确认文件内容和 manifest 一致。来源中心上本来就坏掉的源，导入后仍然是 unavailable，在报告里列出来。
   - 生产上有 43 个 `external` 源，按设计就是 unavailable，验收 1 的"全部 available"不包括它们。
5. **其他：**
   - 多个任务共用的附件，zip 里只存一份。
   - 引用了未导出作业的结果，在报告里列为悬空。
   - 导出前检查导出缓存所在磁盘的剩余空间，不够就拒绝，并说明需要多少。全量大约 50 GB。

## 验收

1. 在测试中心造几个任务，带作业、结果、附件、盲评、接续关系，再加若干没挂任务的作业。导出全部，导入到一个空中心：
   - 任务页、交付报告、盲评图片、结果原件都能打开。
   - 结果源的状态全部是 available。
2. 只导出一部分任务，再导入：
   - 导入的任务数据完整。
   - 没导出的任务不出现。
   - 悬空的接续引用在报告里列出来。
3. 子数据只选一部分的请求，被服务端拒绝。
4. 同一个 zip 导两次：第二次全部跳过，数据不变。
5. 改坏 zip 里一个字节：导入整体拒绝，目标中心不变。
6. 同 ID 不同内容：导入整体中止，列出冲突，目标中心不变。
7. 拿生产数据实际跑一次（lead 做）：
   - 从当前中心选几个任务导出，导入到 rhodes1 的测试中心，人工对照页面。
   - 再导出全部，核对大小和数量，和 rhodes1 上的 rsync 结果对比。
